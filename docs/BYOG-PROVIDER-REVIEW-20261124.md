# CYB BYOG provider review — 24 November 2026

## Money flow and release posture

The target flow is a merchant-owned provider account, key and provider agreement. Checkout requests are sent server-to-server with that merchant's credentials and are not routed through a CYB platform balance. CYB commission is zero. Live merchant keys are rejected by the first adapter. The separate CYB lifetime checkout and its Stripe settings are outside this merchant-payment system.

No provider is represented as approved or operational for CYB. The adapter and screens are test-only foundations. Tap checkout remains closed unless `TAP_PLATFORM_TEST_APPROVED=true` is explicitly configured after written provider authorization. Credentials require `PAYMENT_CREDENTIALS_ENCRYPTION_KEY` (32-byte hex) and are AES-256-GCM encrypted before database storage.

## Implemented test foundations

- Provider adapter interface boundary implemented around Tap's hosted Charge, charge retrieval and refund APIs.
- Dashboard: provider inventory, connect/disconnect, key validation, connection status, country/currency, test/live indication, 0% commission, transaction history and full refund action. No secret key is returned to the client.
- Test key only; encrypted with AES-256-GCM. Live keys are rejected. The checkout is inaccessible until a test key is authenticated and the Tap platform approval gate is enabled.
- Storefront checkout calculates the amount from the stored order, uses a stable Tap idempotency reference, and returns a Tap-hosted URL. Only AED is enabled for the first country rollout, and only after the gate is enabled. Tap controls the hosted payment-method list according to merchant configuration.
- Server retrieves the charge before confirming payment. It compares order, amount, currency and test mode. Signed Tap webhook uses the documented HMAC hashstring, then re-fetches provider state. Event writes are idempotent.
- Refunds are submitted to the connected merchant's Tap account; duplicate refund requests use a stable idempotency reference. A paid Tap order cannot be manually refunded or cancelled before a provider-confirmed refund.
- COD and the existing $246 platform checkout remain separate. Existing Stripe platform code and PR #101 are not edited.
- Merchant configuration, transaction records, webhooks and order mutations are scoped by `businessId`.

## Owner/provider actions before sandbox QA

1. Ask Tap support/account manager to confirm in writing: CYB may let merchants securely supply their own Tap test/live API keys to a website-builder platform; each resulting charge is made directly in the merchant's own account with zero destination transfers, platform fee or CYB balance; and this design is allowed under Tap's platform policy. If not, ask what authorized Tap platform setup provides direct merchant settlement without marketplace collection/liability.
2. Obtain a Tap test merchant account/key and configure `PAYMENT_CREDENTIALS_ENCRYPTION_KEY` on an isolated development/staging API. Do not configure live credentials.
3. Only after Tap's confirmation set `TAP_PLATFORM_TEST_APPROVED=true` in the isolated sandbox environment. Then run authenticated Tap success, decline, webhook replay, duplicate-click, COD exclusion, refund and merchant-isolation QA.
4. For UAE live readiness, obtain Tap's written merchant account, payment-method, settlement, refund and platform authorization details. Do not set any live-mode capability through this branch.
